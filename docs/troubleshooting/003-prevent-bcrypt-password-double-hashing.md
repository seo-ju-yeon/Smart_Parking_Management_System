# TS-003: 관리자 정보 수정 시 BCrypt 해시가 다시 해싱될 수 있었던 문제

## 증상

비밀번호 저장 방식을 BCrypt로 변경하는 과정에서, 관리자가 비밀번호를 바꾸지 않고 이름이나 이메일만 수정해도 기존 BCrypt 해시가 다시 해싱될 수 있었습니다. 이중 해싱된 값이 DB에 저장되면 사용자가 기존 평문 비밀번호를 입력해도 로그인 검증에 실패합니다.

## 재현 흐름

1. 평문 비밀번호 `P`를 BCrypt로 해싱한 `H1`이 DB에 저장되어 있습니다.
2. 관리자 정보를 조회하면 `ManagerVO.password`에 DB의 `H1`이 담깁니다.
3. 비밀번호 입력 없이 이름이나 이메일만 수정하는 코드가 기존 비밀번호를 유지하기 위해 `H1`을 수정 객체에 다시 담습니다.
4. DAO가 전달받은 값을 항상 새 비밀번호로 판단하여 BCrypt를 적용하면 `H2 = BCrypt(H1)`이 저장됩니다.
5. 로그인 시 `P`와 `H2`를 비교하면 일치하지 않습니다. `H2`는 `P`가 아니라 `H1`을 입력값으로 생성한 해시이기 때문입니다.

```text
최초 저장
평문 P → BCrypt → H1 저장

잘못된 정보 수정
기존 해시 H1 → BCrypt → H2 저장

다음 로그인
BCrypt.checkpw(P, H2) → false
```

## 관찰한 코드 흐름

관리자 수정 코드에는 두 종류의 값이 같은 `ManagerVO.password` 필드로 전달되는 경로가 있었습니다.

- 사용자가 새 비밀번호를 입력한 경우: 평문 비밀번호
- 비밀번호를 변경하지 않는 경우: DB에서 조회한 기존 BCrypt 해시

DAO가 값의 의미를 구분하지 않고 모든 비어 있지 않은 문자열을 해싱하면 기존 해시도 평문처럼 처리됩니다. 문제의 핵심은 BCrypt 자체가 아니라 하나의 필드가 평문 입력과 저장된 해시라는 서로 다른 의미를 함께 가진 상태였습니다.

## 원인

관리자 수정 요청에서 비밀번호 변경 여부를 명시적으로 전달하지 않고 `password` 문자열의 내용으로 판단한 것이 원인이었습니다. 기존 해시와 새 평문 비밀번호가 같은 자료형과 같은 필드를 사용하므로 DAO가 두 값을 구분하지 못하면 이중 해싱이 발생합니다.

BCrypt는 같은 평문을 다시 검증할 수 있도록 설계된 단방향 해시이지만, 이미 생성된 해시 문자열을 다시 해싱해도 원래 평문과의 관계가 유지되는 것은 아닙니다.

## 검토한 대안

### 1. 수정 요청의 비밀번호를 항상 해싱

새 비밀번호 처리에는 사용할 수 있지만 기존 해시가 전달되는 경로에서 이중 해싱이 발생하므로 제외했습니다.

### 2. 비밀번호 변경 여부에 따라 수정 메서드와 SQL을 완전히 분리

비밀번호를 바꾸지 않는 요청은 `password` 열을 UPDATE 대상에서 제외하고, 새 비밀번호가 있는 요청만 별도 메서드에서 해싱하는 방법입니다. 평문과 해시를 같은 필드로 구분하는 문제를 줄일 수 있어 구조적으로 더 명확하지만, 당시 여러 관리자 수정 경로를 함께 변경해야 하므로 적용 범위가 컸습니다.

### 3. 빈 값과 BCrypt 형식을 구분하여 처리

현재 구조를 유지하면서 다음 세 경우를 DAO에서 구분할 수 있습니다.

- 비밀번호가 비어 있음: `password` 열을 제외하고 이름과 이메일만 수정
- 60자이며 `$2a$`로 시작함: 기존 BCrypt 해시로 판단하여 그대로 유지
- 그 외의 값: 새 평문 비밀번호로 판단하여 BCrypt 해싱 후 저장

기존 수정 흐름의 변경 범위를 줄이면서 이중 해싱을 막을 수 있어 이 방법을 적용했습니다.

## 해결

`ManagerDAO.updateManager()`에서 비밀번호 값을 다음 순서로 처리하도록 변경했습니다.

1. 비밀번호가 `null` 또는 공백이면 비밀번호를 변경하지 않는 SQL을 사용합니다.
2. 값이 BCrypt 해시 형식이면 다시 해싱하지 않고 기존 값을 사용합니다.
3. 그 외의 값만 `PasswordUtil.hashPassword()`로 해싱합니다.

관리자 수정 화면의 비밀번호 입력란은 기존 해시를 화면에 출력하지 않고 비워둡니다. 사용자가 값을 입력한 경우에만 새 비밀번호로 처리합니다.

### 변경 후 흐름

```text
비밀번호 입력 없음
→ password 열을 제외하고 정보 수정

기존 해시 전달
→ BCrypt 형식 확인
→ 다시 해싱하지 않고 H1 유지

새 평문 비밀번호 입력
→ BCrypt 해싱
→ 새 해시 저장
```

## 검증

### 코드 확인

- `ManagerModifyController`는 비밀번호를 입력하지 않은 일부 수정 경로에서 DB의 기존 해시를 수정 객체에 유지합니다.
- `ManagerDAO.updateManager()`는 빈 값, 기존 BCrypt 해시, 새 평문 비밀번호를 분기합니다.
- 관리자 수정 JSP의 비밀번호 입력란에는 기존 해시를 `value`로 출력하지 않습니다.

### 자동 검증

`./gradlew test --tests org.example.smart_parking_260219.util.PasswordUtilTest`를 실행했습니다.

| 테스트 클래스 | 실행 | 실패 | 오류 | 결과 |
| --- | ---: | ---: | ---: | --- |
| `PasswordUtilTest` | 6 | 0 | 0 | 통과 |

현재 테스트는 BCrypt 해시 생성, 정상·비정상 비밀번호 비교, 솔트에 따른 해시 차이와 잘못된 입력 처리를 확인합니다. `ManagerDAO.updateManager()`의 이중 해싱 방지 분기를 직접 실행하는 회귀 테스트는 아직 없으므로, 위 결과만으로 DAO 분기 전체가 자동 검증되었다고 보지는 않습니다.

### 수동 검증 기록

개발 과정에서 관리자 정보 수정 후 기존 비밀번호로 로그인하지 못하는 현상을 기준으로 원인을 추적했습니다. 당시 반복 횟수와 DB 해시 변경 전·후 값을 별도로 보관하지 않았으므로 수동 검증 통과 횟수는 기재하지 않습니다.

## 결과

- 이름이나 이메일만 수정할 때 기존 BCrypt 해시를 다시 해싱하지 않습니다.
- 새 비밀번호를 입력한 경우에만 새 BCrypt 해시를 생성합니다.
- 비밀번호를 변경하지 않는 수정으로 기존 평문 비밀번호와 해시의 대응 관계가 깨지는 경로를 차단했습니다.

## 남은 한계

현재 방어는 문자열 길이와 `$2a$` 접두사로 기존 해시를 판별합니다. 평문과 해시를 동일한 `password` 필드로 전달하는 구조 자체는 남아 있습니다. 이후 테스트를 정비할 때는 비밀번호 변경 전용 입력 모델이나 DAO 메서드로 분리하고, Testcontainers 기반 DAO 회귀 테스트로 기존 해시 유지 여부를 확인할 필요가 있습니다.

## 배운 점

비밀번호 해싱은 저장 시점뿐 아니라 수정 흐름까지 함께 검토해야 합니다. 평문 비밀번호와 저장된 해시는 모두 문자열이지만 의미가 다르므로, 값의 모양만으로 구분하기보다 비밀번호 변경 의도를 명시적인 요청 모델이나 메서드로 표현하는 것이 더 안전합니다.
