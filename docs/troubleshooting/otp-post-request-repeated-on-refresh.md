# 새로고침 시 OTP 실패 횟수가 다시 증가한 문제

## 문제 상황

로그인 OTP를 잘못 입력하면 남은 입력 횟수가 즉시 갱신되지 않았다.

오류 화면에서 새로고침하면 남은 횟수가 갱신되었지만, 새로고침할 때마다 실제로 OTP를 다시 입력하지 않았는데도 실패 횟수가 계속 증가했다.

## 원인 확인

OTP 검증 실패 후 `forward()`로 JSP를 표시하고 있었다.

`forward()`는 서버 내부에서 화면만 변경하므로 브라우저가 마지막으로 요청한 POST 요청은 그대로 남는다. 따라서 사용자가 새로고침하면 브라우저가 OTP 검증 POST 요청을 다시 전송했고, 서버는 이를 새로운 인증 실패로 처리하여 실패 횟수를 증가시켰다.

### 기존 흐름

```text
OTP 입력
→ POST 요청
→ 인증 실패 횟수 증가
→ JSP로 forward
→ 사용자가 새로고침
→ 동일한 POST 재요청
→ 실패 횟수 다시 증가
```

## 검토한 대안

### 1. 기존 `forward()` 유지

구현은 단순하지만 새로고침으로 POST 요청이 반복되는 문제를 해결할 수 없다.

### 2. JavaScript로 새로고침 차단

브라우저 동작에 의존하며 개발자 도구나 직접 요청을 통해 우회할 수 있다. 서버의 요청 처리 문제를 클라이언트에서 막는 방식이므로 선택하지 않았다.

### 3. PRG 패턴 적용

POST 처리 후 화면을 직접 반환하지 않고 GET 요청으로 리다이렉트한다. 오류 메시지는 세션에 잠시 저장하고 다음 GET 요청에서 한 번만 사용한다.

## 결정 및 해결

OTP 검증 요청에 PRG(Post/Redirect/Get) 패턴을 적용했다.

1. POST에서 OTP를 검증하고 실패 횟수를 변경한다.
2. 오류 메시지를 세션에 Flash Message로 저장한다.
3. OTP 입력 화면으로 리다이렉트한다.
4. GET에서 메시지를 request로 옮긴 뒤 세션에서 삭제한다.

### 개선된 흐름

```text
OTP 입력
→ POST 요청
→ 인증 실패 횟수 증가
→ 오류 메시지를 세션에 임시 저장
→ 302 Redirect
→ GET 요청
→ 오류 메시지 표시 후 삭제
→ 새로고침해도 GET만 반복
```

## 결과

- 실제로 OTP를 제출했을 때만 실패 횟수가 증가한다.
- 새로고침해도 실패 횟수가 추가로 증가하지 않는다.
- 오류 메시지는 리다이렉트 후 한 번만 표시된다.
- 브라우저 Network 탭에서 `POST → 302 → GET` 흐름을 확인했다.

## 배운 점

`forward()`와 `redirect()`는 단순히 화면을 이동하는 방법의 차이가 아니다. 데이터를 변경하는 POST 요청 이후에는 PRG 패턴을 사용해야 새로고침으로 동일한 요청이 반복되는 문제를 방지할 수 있다는 것을 확인했다.
